# QRWink

**把文件变成一串二维码在屏幕上轮播，另一台机器录屏把画面捡回来。**

给「两端不能有任何网络连接」的场景用的：发送端是一台隔离机，只有一块屏幕；
接收端是另一台机器，只有一只摄像头（或者远程桌面看这一块屏幕）。
中间没有 U 盘、没有网络、没有任何服务端。

整条链路只用到 **canvas 2D + 两个纯 JS 库**：不依赖 WASM，不依赖 WebGL，不依赖 HTTP 服务。
发送端双击 `sender/send.html` 就能跑（`file://` 直接打开），隔离机不需要装任何东西。

```
┌──────────── 隔离机 ────────────┐        ┌──────────── 接收机 ────────────┐
│  send.html（单文件 94 KB）      │        │  recv.html（单文件 309 KB）     │
│  文件 → 分帧 → QR → 屏幕上轮播  │ ──屏幕──▶│  录屏 → 拆通道 → 解码 → 拼回文件 │
└────────────────────────────────┘  光/线  └────────────────────────────────┘
```

## 快速开始

### 发送端（隔离机）

把 `sender/send.html` 拷过去，双击打开。界面默认**只有二维码**，其他都藏起来。

| 操作 | 效果 |
|---|---|
| 把文件拖进窗口 | 载入并开始 |
| 点一下画面 | 开始 / 暂停 |
| 滚轮 | 前/后换一屏（自动暂停） |
| 鼠标移到窗口里 | 浮出控制条，2 秒后自动消失 |
| 拖控制条上的进度 | 跳到任意一屏 |
| 空格 / ← → / `F` | 暂停、前后换屏、全屏 |

控制条右下角显示**实测**换屏速率和 KB/s（滚轮手动切也计入，按最近 3 秒窗口算）。
窗口建议开到 1000 px 上下 —— 太大了每个模块的像素变多，接收端解码反而变慢。

### 接收端（接收机）

`getDisplayMedia` 要求安全上下文，`file://` 不行，所以要起一个本地 http：

```bash
python receiver/serve.py          # 起在 127.0.0.1:8765，自动打开浏览器
# 或者手动访问 http://127.0.0.1:8765/recv.html
```

点「开始采集」，选发送端那个窗口（比选整个屏幕更稳）。收齐后自动校验 CRC 并给出保存链接，
文件名就是发送端那个文件的本名。

**收完一个可以接着收下一个**：捕获流和锁定区域都不动，发送端换一个文件，接收端自动开始收新的，
最近 6 个文件的保存链接都留在页面上。只有点「停止」才会真正断开采集。

## 为什么是这个设计

| 约束 | 应对 |
|---|---|
| 隔离机没有 GPU 驱动，WebGL2 起不来 | 只用 canvas 2D，二维码用 `drawImage` 缩放绘制 |
| 不能装软件、不能起服务 | 发送端是**单文件 HTML**，`file://` 直接跑 |
| 远程桌面会掉帧、会把画面缩放 | 每帧自带校验，坏帧当场丢，靠循环重播补 |
| 浏览器解码是纯 CPU | 解码放 Worker 池并行，只解「锁定住的那一小块」 |
| 慢机器上编码也贵 | 编码放 Worker 池并行 + 掩码复用（见下） |

## 工作原理

### 帧格式：33 字符定长头

```
WNK | idx4 | total4 | ver2 | size8 | crc8 | fcrc4 | 载荷(base44)     ← 数据帧
WNM | 0000 | total4 | ver2 | size8 | crc8 | fcrc4 | 载荷(base44)     ← 文件名帧
WNT | pass2 | stage1 | total3 | seq3 | fps2 | 数字填充                ← 测速模式
```

- 全部字段是**定长大写十六进制**、没有分隔符，所以载荷里可以出现 `:`（base44 要用到）。
- `fcrc` 是 16 位 CRC，覆盖 `idx + 载荷`：**收到一帧就能当场判断好坏**，坏的直接丢，
  等发送端下一轮重播，不会污染已经收好的其它帧。
- 所有帧等长 → 所有帧同一个 QR 版本 → 屏幕上二维码尺寸恒定，接收端不会因尺寸跳变而失手。

**每屏都是独立可发的**：每一屏自带帧号、总帧数、文件大小、整包 CRC 和帧级校验，
接收端收哪一屏算哪一屏，跳着发、倒着发、只发中间一段都能拼回去。
唯一例外是第 0 屏的文件名帧：跳过它，接收端会等 1.5 秒后用 `received.bin` 保存，内容不丢。

### base44：比字节模式多装 45%

二维码的「字母数字」模式（`0-9 A-Z` 和 `$%*+-./:`）每字符只用 5.5 bit，比字节模式的 8 bit 划算。
把字节流按 base45 的规则编成 44 个字符（**去掉空格**，避免首尾空白被裁剪或忽略）：

```
2 字节 → 3 字符（0..65535 → 44³ 进制）
末尾剩 1 字节 → 2 字符
```

实测同一尺寸（v26，121 模块）下：字节模式 1367 字符，字母数字模式 1990 字符。

**帧长必须是 3 的倍数**；另外文件长度为奇数时，最后一组只有 2 字节，
必须先补一个零字节再编码，否则最后一字节会被编错（这个坑踩过一次，现在发送端会自己补）。

### RGB 三通道：一屏装三个帧

同一个位置，R / G / B 三个通道各画一个**不同的帧**。每个通道单独看就是一张普通的单码图，
所以解码器完全不用改，只要把某个通道拆成灰度图再交给 jsQR。
jsQR 的亮度公式是 `0.2126R + 0.7152G + 0.0722B`，整幅解码拿到的是 G 通道，
所以接收端靠**扫像素判断有没有颜色**来决定走三通道还是灰度，不靠解码结果瞎猜。

实测（113 模块、JPEG 0.15~无损，模拟 4:2:0 色度子采样）：

| 模块像素 | 画布 | 无损 | 0.65 | 0.45 | 0.25 | 0.15 |
|---|---|---|---|---|---|---|
| 8 | 904 | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 |
| 6 | 678 | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 |
| 4 | 452 | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 |
| 3 | 339 | 3/3 | 3/3 | 2/3 | 1/3 | 0/3 |

**每模块 ≥4 像素时三通道都稳**。低于 3 像素色度就糊了，这时切「灰度 ×1」。
发送端下拉框可以随时切，接收端会自己认出来。

## 实测性能

### 发送端

一屏 3 帧，每帧都是一张完整的二维码。编码（选版本 + 掩码评估）是纯计算，也是慢机器上的瓶颈。

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| 单帧编码 | 9 ms | **1.6 ms** |
| 一屏（3 帧，单线程） | 55.6 ms | **7.5 ms** |
| 100 帧（3 个 Worker） | 1159 ms | **203 ms** |
| 1071 px 画布持续播放 | — | **10 屏/秒**（设定值上限） |

做到这一步靠四件事：

1. **编码搬进 Worker 池**：`encodeText()` 不碰 DOM，同一份源码在页面和 Worker 里都能跑；
   载入文件后把整份文件排进队列，后台并行编，播放时直接命中缓存。
2. **掩码只评估一次**：qrcode-generator 默认对 8 种掩码各铺一遍矩阵打分、再按最优的铺第 9 遍。
   同一份文件的每帧长度相同、图案结构相同，所以第一次评估完就记住，后面直接复用
   （掩码编号写在格式信息里，解码端照它还原，不影响可解码性）。这是**最大的一笔**。
3. **版本只搜一次**：帧长相同 → QR 版本必然相同，记住第一帧的版本，后面的帧直接用它，
   装不下再回落到完整搜索。
4. **缓存装得下整份文件**：之前缓存上限 40 条，大文件每轮都重编一遍；现在按帧数放大。

### 接收端

解码跑在 Worker 池里，每个通道一个任务，通道缓冲用 `transfer` 交给 Worker、解完原样送回，
不做额外拷贝；主线程只负责采样，一次最多 3 帧在飞（背压）。
**画面没变（指纹相同）就整帧跳过**，不再提交给池子 —— 这一条把「解析」从 4.3 提到 8.6 屏/秒。

同一份 60 KB 载荷：

| 发送帧率 | 接收端用时 | 有效速率 | 解析 | 送解 |
|---|---|---|---|---|
| 3 屏/秒 | 4.0 s | 18.8 KB/s | 3.3 屏/秒 | 3.4 次/秒 |
| 8.3 屏/秒 | **1.5 s** | **45.4 KB/s** | 8.6 屏/秒 | 11.4 次/秒 |

「解析」和「送解」应该接近 —— 差得越大，说明无效提交越多。

只解锁定的那一块（1920×1080 整屏采集、码 612×612）：

| 方式 | 每帧解码 | 上限 |
|---|---|---|
| 整屏扫描 | 92 ms | ~11 屏/秒 |
| 锁定 696×696 | **39 ms** | ~25 屏/秒 |

省下来的全是像素：整屏 207 万，锁定的框只有 48 万。
锁定后预览也只画那一块（四角绿色取景框 + 尺寸标注），不再整幅转播，每 3 秒刷新一次。

**结论**：吞吐跟着发送端线性走，上限在采集帧率（`getDisplayMedia`）和 Worker 池产能，
不在解码算法。

## 构建与测试

改完 `src/*.tpl.html` 之后重新生成两个单文件：

```bash
python tools/build_2d.py
```

它会把两个库内联进去、把 `__TEMPLATE__` 置为 false、回填文件大小，
并断言产物里没有 `</script`（否则单文件会被截断）。

**`src/*.tpl.html` 不是成品**：里面写着 `var __QRCODE__;` 之类的占位符，直接双击会红字报错。

验证脚本（都不需要两台机器、不需要摄像头）：

| 脚本 | 验什么 |
|---|---|
| `python tools/qr2d_roundtrip.py --size 24000` | 闭环：渲染→JPEG 压缩→拆通道解码→拼回→CRC |
| `python tools/recv2d_test.py --size 30000` | 端到端：真实接收端 + 伪造的屏幕采集流，含坏帧注入 |
| `python tools/recv2d_test.py --ch 1` | 同上，走灰度模式 |
| `python tools/recv2d_test.py --expect 2` | 连收两个文件，验证收完一个还能接着收 |
| `python tools/ui_seek_check.py` | 交互：默认隐藏、点击暂停、滚轮换屏、进度条拖拽 |
| `python tools/color3_check.py` | 三通道在不同压缩质量下的余量 |
| `python tools/layout_check.py` | 发送端在 6 种窗口尺寸下，二维码是否被底部控制条盖住 |
| `python tools/send_rate_check.py --size 185000` | 发送端实测换屏速率与编码耗时 |
| `python tools/frame_dump.py --size 184999` | 把发送端每一帧导出、本机拼回验 CRC |
| `python tools/diag_recv.py` | 接收端启动自检：库是否就位、Worker 池是否建起来 |

`recv2d_test.py` 的 `--hold 60` 模拟「拉着进度条快速滚」，`--noworker` 对比单线程，
`--screen 1920x1080` 把码放进大画面里模拟整屏共享，`--noroI` 关掉区域锁定做对比。
`--corrupt N` 会在第 N 屏连续两次塞一个「格式合法、内容错」的码，用来验证帧校验；
**测吞吐时请用 `--corrupt -1`**，否则那一屏会被反复判废、把总时长拖长。
`--shot out.png` 把接收端预览图存下来，方便眼看标记和取景框。

### 改测试脚本必须遵守：浏览器 profile 只能复用，不能新建

**任何 `--user-data-dir` 都必须来自 `_browser.profile_dir(tag)`，禁止 `tempfile.mkdtemp`
之后再指给浏览器。**

原因（2026-11-25 真事故）：Chromium 系浏览器在**首次**创建某个 user-data-dir
（生成 `Local State`）时，会拿当前 Windows 账户发起一次交互式 `LogonUser`
（Negotiate、密码为空）——必然失败，并往安全日志写一条 **4625**。
每轮测试 mkdtemp 一个新目录，就等于每轮往账户的失败登录计数器上加次数：

| 现象 | 数值 |
|---|---|
| 当天 4625 累计 | 225+ 条（223 条来自 chrome.exe） |
| 账户被锁 | 10 次（4740），锁 10 分钟，解锁后不到 1 分钟又被拉满 |
| 后果 | 用户自己被挡在门外；为继续工作只能临时关闭锁定策略，整机失去爆破防护 |

现在的做法：

```python
from _browser import profile_dir, work_dir
prof = profile_dir("recv")         # %TEMP%\wink-prof\recv，永久复用
work = work_dir("wink-2d-")        # 本轮产物目录，退出自动删
```

* `profile_dir()` 会先塞一份现成的 `Local State`（从本机 Chrome/Edge 的 profile 拷），
  这样连第一次也不会走「初始化 profile」那条路径
* 目录**永不删除** —— 删掉再重建就会重新触发，等于把问题请回来
* 用完的浏览器进程用 `kill_by_profile(prof)` 按路径杀（Chrome 启动后会换 PID）
* 历史垃圾：`python tools/_browser.py --clean-dirs`（只清 `wink-*` 产物目录，不动 `wink-prof`）

自查（需要管理员权限读安全日志）：

```powershell
(Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625; StartTime=(Get-Date).AddMinutes(-30)}).Count
```

跑几轮之后这个数必须还是 0。

## 排错

**页面全白 / 红字报错**
先看红字。最常见的是打开了 `src/*.tpl.html`（模板）而不是 `sender/send.html`。
「编码库没有加载成功」多半是文件被截断，红字里有实际字节数，和 `send.html` 的真实大小对一下。

**收齐了但校验不过**
多半是两端版本不一致。本版起帧头魔术字改成了 `WNK`，旧版发送端和这个接收端不互通。

**接收端一格都收不到**

1. 远程桌面有没有被缩放（必须 1:1）
2. 发送端窗口是不是被别的窗口挡住了一部分
3. 点「开始采集」时选的是整个屏幕还是那个窗口 —— 选窗口更稳
4. 灰度/彩色模式对不对（发送端控制条上能看到当前模式）

**接收速率比发送低**
看状态栏的「解析 X 屏/秒」和「送解 X 次/秒」。解析明显低于发送端帧率，
通常是接收页被切到后台或被挡住（浏览器会把 `requestAnimationFrame` 限到约 1 Hz）。

**文件名变成了 received.bin**
第 0 屏（文件名帧）没收到。用进度条回到第一屏停一下就行，内容不受影响。

## 已知限制

- **必须 1:1**：画面被缩放后模块像素不是整数，解不出来。远程桌面要关掉「智能缩放」。
- **色彩通道依赖显示链路**：RDP 的 4:2:0 色度子采样在每模块 ≥4 像素时扛得住，更低就该切灰度。
  任何「锐化/降噪/增强」类后期都会毁掉色度。
- **吞吐上限在通道不在算法**：RDP 一般限制在 4~10 帧/秒，再快也就这样。
- **单次别传太大**：10 MB 以上建议先压缩，或者只传关键文件。
- **Worker 建不起来会自动退回单线程**：仍能工作，只是慢一些。
