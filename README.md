# QRWink

**把文件变成一串二维码在屏幕上轮播，另一台机器录屏把画面捡回来。**

用于两端**不能有任何网络连接**的场合：发送端只有一块屏幕，接收端只能看这块屏幕。
不需要 U 盘，不需要联网，不需要服务端，也不需要装任何软件。

```
┌────────── 发送端（如隔离机）──────────┐      ┌────── 接收端（如办公 PC）──────┐
│  send.html（单文件，94 KB）            │      │  recv.html（单文件，309 KB）    │
│  文件 → 分帧 → 二维码 → 屏幕轮播       │ ───▶ │  录屏 → 拆通道 → 解码 → 还原文件 │
└────────────────────────────────────────┘ 屏幕 └────────────────────────────────┘
```

## 特点

- **单文件，双击即用**：发送端是纯 HTML，`file://` 直接打开，不需要服务器、不需要 WASM、不需要 WebGL
- **丢帧自愈**：发送端循环播放，接收端只补缺的那几帧；跳着看、中途开始看都能拼出完整文件
- **一屏三个帧**：利用 RGB 三通道并行传输，吞吐是单码的三倍
- **收完一个接着收下一个**：不用重新选采集区域

## 快速开始

### 发送端

把 `sender/send.html` 拷到要发文件的机器上，双击打开。

| 操作 | 效果 |
|---|---|
| 把文件拖进窗口 | 载入并开始发送 |
| 点一下画面 | 开始 / 暂停 |
| 滚轮 | 前 / 后换一屏 |
| 鼠标移到窗口里 | 浮出控制条，2 秒后自动隐藏 |
| 拖控制条上的进度 | 跳到任意一屏 |
| 空格 / ← → / `F` | 暂停、前后换屏、全屏 |

控制条显示**实测**换屏速率和 KB/s。窗口开到约 1000 px 最合适：更大不会更快，
反而让接收端每帧要多解很多像素。

### 接收端

录屏 API 要求安全上下文，`file://` 不行，所以需要本地起一个静态服务（只需要 Python）：

```bash
python receiver/serve.py
# 自动打开 http://127.0.0.1:8765/recv.html
```

点「开始采集」，选择发送端那个窗口（比选整个屏幕更快、更稳）。
收齐后自动校验并给出保存链接，文件名就是原文件名。

收完一个文件后采集不会中断：换一个文件继续发，接收端会自动开始收新的，
最近 6 个文件的链接都留在页面上。

## 工作原理

### 帧格式

每个二维码承载一帧，帧头是 33 个字符的定长字段：

```
WNK | idx4 | total4 | ver2 | size8 | crc8 | fcrc4 | 载荷(base44)     数据帧
WNM | 0000 | total4 | ver2 | size8 | crc8 | fcrc4 | 载荷(base44)     文件名帧
WNT | pass2 | stage1 | total3 | seq3 | fps2 | 数字填充               测速模式
```

- 字段是定长大写十六进制、无分隔符，因此载荷里可以出现 `:`（base44 需要）
- `fcrc` 覆盖 `idx + 载荷`：每帧独立校验，坏的当场丢弃，等下一轮重播补上，不会污染已收好的帧
- 所有帧等长 → 所有帧用同一个 QR 版本 → 屏幕上的二维码尺寸恒定，解码端不会因尺寸跳变而失败

因为每帧都自带帧号、总帧数和整包 CRC，**任意屏都可以单独发送**：跳着发、倒着发、
只发中间一段都能还原。唯一的例外是文件名为第 0 屏，跳过它只影响文件名，不影响内容。

### base44：比字节模式多装 45%

二维码的字母数字模式（`0-9 A-Z` 和 `$%*+-./:`）每字符只占 5.5 bit，比字节模式的 8 bit 更省。
把字节流按 base45 的规则映射到 44 个字符（去掉空格，避免首尾空白被裁剪）：

```
2 字节 → 3 字符（0..65535 按 44³ 进制）
末尾剩 1 字节 → 2 字符
```

相同尺寸下，字母数字模式比字节模式多装约 45%。

### RGB 三通道：一屏三个帧

同一位置，R、G、B 三个通道各画一个**不同的帧**。每个通道单独看就是一张普通二维码，
所以解码器无需任何改动，只要把某个通道取出来当灰度图即可。
接收端通过检查画面是否有颜色来判断该走三通道还是灰度模式。

三通道能否还原取决于每个模块的屏幕像素数（模拟 4:2:0 色度子采样下的测试）：

| 每模块像素 | 画布 | 无损 | 压缩 0.45 | 压缩 0.15 |
|---|---|---|---|---|
| 8 | 904 | 3/3 | 3/3 | 3/3 |
| 6 | 678 | 3/3 | 3/3 | 3/3 |
| 4 | 452 | 3/3 | 3/3 | 3/3 |
| 3 | 339 | 3/3 | 1/3 | 0/3 |

**每模块 ≥4 像素时三通道都可靠**；低于 3 像素色度会被压糊，此时应改用「灰度 ×1」模式。
发送端可以随时切换，接收端会自动识别。

## 性能

以窗口约 600 px、每帧 2799 字符（约 1.9 KB）、三通道为例：

| 指标 | 数值 |
|---|---|
| 每屏数据量 | 5.5 KB |
| 帧率可选 | 2 / 3 / 4 / 6 / 8 / 10 屏每秒 |
| 3 屏/秒 | 约 16 KB/s（1 MB 约 1 分钟） |
| 8 屏/秒 | 约 45 KB/s（1 MB 约 23 秒） |
| 单屏解码耗时 | 26–60 ms（锁定区域后） |

提高密度（每帧 4197 字符）可到每屏 8.2 KB，3 屏/秒约 25 KB/s。
实际能跑多快，看接收端状态栏的「解析 X 屏/秒」——它跟上发送端的帧率时，就是当前通道的极限。

接收端会记住二维码在屏幕上的位置，之后只解析那一小块：

| 采集方式 | 每帧解码耗时 |
|---|---|
| 1920×1080 整屏扫描 | 92 ms |
| 只解锁定区域（约 700×700） | 39 ms |

解码在 Web Worker 池中并行进行，界面不会卡顿。

## 构建与测试

修改 `src/*.tpl.html` 后重新生成两个单文件：

```bash
python tools/build_2d.py
```

`src/*.tpl.html` 是模板（含占位符），不能直接打开；`sender/send.html` 和
`receiver/recv.html` 才是成品。

测试脚本不需要两台机器或摄像头：

| 命令 | 检查内容 |
|---|---|
| `python tools/qr2d_roundtrip.py --size 24000` | 渲染 → JPEG 压缩 → 拆通道解码 → 还原 → CRC |
| `python tools/recv2d_test.py --size 30000` | 端到端：真实接收端 + 模拟采集流 |
| `python tools/recv2d_test.py --ch 1` | 同上，灰度模式 |
| `python tools/recv2d_test.py --expect 2` | 连续接收两个文件 |
| `python tools/ui_seek_check.py` | 交互：暂停、滚轮换屏、进度条拖拽 |
| `python tools/layout_check.py` | 多种窗口尺寸下二维码是否被遮挡 |
| `python tools/send_rate_check.py --size 185000` | 发送端实测帧率与编码耗时 |

更多参数见各脚本的 `--help`。

> 修改测试脚本时请注意：浏览器必须复用 `tools/_browser.py` 提供的固定 profile 目录
> （`profile_dir()`），不要每次新建。原因写在 `_browser.py` 的文档字符串里。

## 常见问题

**收不到任何画面**

1. 远程桌面是否开启了画面缩放 —— 必须是 1:1
2. 发送端窗口是否被其他窗口遮挡
3. 采集时选的是整个屏幕还是那个窗口 —— 选窗口更稳定
4. 发送端窗口是否小于 600 px（模块像素不足）

**收齐了但校验不通过**

两端版本不一致。帧头标识为 `WNK`，旧版本与本版本不兼容。

**接收速率明显低于发送端帧率**

看接收端状态栏的「解析 X 屏/秒」。如果远低于发送端，通常是接收页面被切到后台或
被其他窗口遮挡（浏览器会限制后台页面的刷新频率），让页面保持可见即可。

**文件名变成 received.bin**

第 0 屏（文件名帧）没收到。用进度条回到第一屏停几秒即可，内容本身不受影响。

## 已知限制

- **画面必须 1:1**：缩放后模块像素不是整数，无法解码
- **三通道依赖显示链路**：RDP 等会做色度子采样的环境，每模块需 ≥4 像素；更低请用灰度
- **吞吐受通道限制**：远程桌面通常只有 4~10 帧/秒，再快也没有收益
- **大文件耗时较长**：10 MB 以上建议先压缩
